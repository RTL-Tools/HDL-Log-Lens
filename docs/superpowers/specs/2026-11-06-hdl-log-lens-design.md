# HDL Log Lens — Design

## Intent

HDL engineers (here: one, working in a Makefile-driven open-source FPGA flow) get warnings and errors from several tools, each in its own log file in its own format. Today they scroll terminals and logs by hand. HDL Log Lens is a VS Code extension that reads those logs from disk and puts the warnings and errors in the built-in **Problems panel**, so they can be filtered by file and severity and clicked to jump to the source line.

Why a log-file extension rather than `tasks.json` problem matchers: it parses logs left on disk by earlier runs and ships a ready-made parser per tool, with no per-project matcher setup.

## Goals

- Parse logs from **Verilator, NVC, Yosys, nextpnr** into diagnostics (file, line, column/range, severity, code, message).
- Show them in the Problems panel via one `DiagnosticCollection` (grouping, filtering, go-to-line come free).
- Find logs by glob setting; re-parse a log when it changes; clear that log's old diagnostics on re-parse.
- Auto-detect the tool per log (banner or filename), with a setting to override.
- Resolve paths in order: absolute → relative to the log's directory → workspace root → filename search.
- De-duplicate identical diagnostics (same file, range, severity, code, message) within a log. Yosys repeats warnings (e.g. 4× `m_axi.tdata` at `sbox.sv:129`); each should appear once.
- Location-less messages (most of nextpnr, NVC `Fatal` with no source) attach to the log file itself, line 1.
- `source` = tool name (`verilator`), `code` = message ID where one exists (`UNUSEDSIGNAL`).
- Commands/settings: "Clear HDL problems"; setting to suppress message IDs.
- Tests against **real log fixtures** from the AES project.

## Non-goals (v1)

- **Vivado and Questa parsers.** Deferred until the user has a machine with both tools; no hand-written fixtures from documentation. The parser interface must make adding one a single new file plus a fixture.
- Sidebar `TreeDataProvider` / project dropdown.
- Running builds from the extension. The extension only reads logs.
- GHDL, Icarus, cocotb/VUnit, other tools.

## Anti-goals (a failure even if it "works")

- Stale diagnostics lingering after a clean re-run of the tool. (Staleness after an *editor* edit is a known v1 limitation: diagnostics stay until the log is next re-parsed or the user runs "Clear HDL problems".)
- Duplicated entries flooding the panel.
- Wrong-file jumps from bad path resolution (silently attaching to a different file with the same name).
- Hangs on large logs (Yosys logs are thousands of lines).

## Constraints / decisions made

- VS Code extension, TypeScript, built-in Problems panel via `DiagnosticCollection` (user decision).
- One parser per tool behind a common interface returning `{file, line, col, endLine?, endCol?, severity, code, message}` (user spec).
- Dedupe is required (user decision).
- Yosys ranges `L.C-L.C` map to a start/end range (agreed in discussion).
- Test fixtures come from the AES repo (`/Users/james/Workspace/AES`, user's own project). Its make targets now write logs to `out/reports/{nvc,verilator,yosys}/` (changed in AES during this design; uncommitted there).

## Known formats (from real AES logs)

| Tool | Example | Notes |
|---|---|---|
| Verilator | `%Warning-UNUSEDSIGNAL: /abs/src/axil_if.sv:63:24: Signal is not used: 'awready'` | `%Error` has no ID; `%Error-PINNOTFOUND: …` does. Context lines (`  63 \|`, caret lines, `... See the manual`) follow and must be skipped, not parsed. |
| Yosys | `Warning: wire '\m_axi.tdata' is assigned in a block at /abs/src/sbox.sv:129.11-129.62.` | Location is embedded at end of message, with a range. Summary line `Warnings: 90 unique messages, 106 total` is not a diagnostic. |
| nextpnr | `Warning: IO 'rst_n_i' is unconstrained in LPF…` | No location → log file. Final `4 warnings, 0 errors` is not a diagnostic. |
| NVC | `** Warning: …`, `** Fatal: opening …: No such file` | Source locations, when present, arrive on later `>` lines (state machine). The AES NVC log captured so far has none; a real compile-error fixture must be generated by introducing a VHDL error. |

## Left to the builder

- Project layout, bundler, test runner, activation events, exact setting names.
- Debounce/watch strategy; handling of very large logs.
- How "filename search" is bounded (workspace-limited, cached).
- Windows/WSL path handling: handle reasonably if cheap, otherwise note as a limitation.
- Multi-line message handling per tool beyond the above.
- Whether to attach the workspace folder to `source` for multi-root workspaces (optional; not required in v1).

## Open items (my calls, flagged)

- NVC fixture: I will create a real error log by breaking a copy of an AES VHDL file and running NVC, since the existing log has no source locations. *(My call.)*
- Logs of failed runs are parsed the same as successful ones. *(My call.)*
- Default log glob: `**/out/reports/**/*.log` plus `**/*.rpt`; user-overridable setting. *(My call.)*
- Severity mapping: Verilator `%Error`/`%Warning`; Yosys/nextpnr `ERROR`/`Warning`; NVC `Error`/`Fatal` → Error, `Warning` → Warning, `Note` → Information. Verilator `-Wno-fatal` warnings stay Warnings. *(My call.)*
- De-duplication is within one log only. Identical diagnostics from different logs (e.g. AES's `yosys/yosys.log` and `impl/aes_impl_top_ecp5_synth.log`) are kept, because they are separate tool outputs. *(User decision.)*
